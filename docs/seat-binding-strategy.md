# 席位绑定策略（2026-11-18 重审）

> 触发：用户真机反馈「八席显示的全是我已经关闭的历史对话，找当前对话必须关掉八席」。
> 顺序：先定 eval（`evals.md` §11 STAB），再定策略（本文），最后才动代码。

## 1. 现状（代码事实，不含推测）

| 环节 | 现在的行为 | 位置 |
| --- | --- | --- |
| 播种 | `seeded === false` 时，按会话列表 `ids` **原序**取前 8 个 `eligible`，依次填席 | `reconcile()` 播种段 |
| 候选 | `origin !== "subagent" && parentId === undefined`，**不看归档、不看工作区、不看活跃度** | `isSeatEligible()` |
| 回收 | 仅四类：会话不存在 / 变子会话 / 用户清空 / 同工作区空白槽让位 | `reconcile()` 主循环 |
| 持久化 | `localStorage["dsh-agent-grid.bindings.v3"] = { seeded, bind }` | `BIND_KEY` |
| 归档信息 | 宿主有 `archivedSessionIds`（`dsh-client-ui-workspace` 的 `SessionRowState`），当前**未使用** | 待确认客户端可达路径 |

## 2. 三个失败模式

- **M1 旧会话占位**：播种按列表原序（实测最旧一批在前），且不过滤归档 → 用户关掉的对话占满八席。
- **M2 旁路会话无席**：看板替换了侧栏会话列表，但从原生列表/命令面板/深链/上次会话恢复进来的对话**不占席** → 看板里根本没有它，只能关插件。
- **M3 复活**：绑定表一旦被重置（清空 localStorage、schema 迁移、换机器），播种会重新选中那些已归档会话 →「关掉的又回来了」。

## 3. 设计目标（与 eval 一一对应）

| 目标 | 对应不变量 | 对应 case |
| --- | --- | --- |
| 当前会话必然占一席（无幽灵） | I1 | STAB-07 / STAB-11 |
| 已建立的格子不无故消失 | I2 | STAB-05 / STAB-12 |
| 关掉的对话不自动回来 | I3 | STAB-01 / STAB-04 |
| 新会话不静默抢占 | I4 | STAB-09 / STAB-10 |
| 播种规则可解释、可重放 | I5 | STAB-02 / STAB-03 |
| 重启前后一致 | I6 | STAB-12 |

## 4. 策略

### S1 播种（改）

```
候选 = 当前工作区成员
      − 已归档（archivedSessionIds）
      − 子会话
排序 = [当前会话] → updatedAt 倒序
取前 8 个；不足 8 个就留「虚席」，不拿别的会话凑数
```

- **只服务当前工作区**：跨工作区的会话不进看板，避免「切个目录八席全变」。
- **不做自动补位**：`seeded` 之后维持现有「绑定归用户」语义（RT-BIND-04 不变）。

### S2 归档与绑定的关系（新增规则，但不新增解绑条件）

- 归档**只影响播种**（I3），**不影响已建立的绑定**（I2）。
- 已绑会话被归档 → 格子保留、显示「休息」，用户仍可点开历史。
- 理由：把「收起历史」变成「格子消失」，比占着一个格更伤；想腾格子就让用户点「收工」。

### S3 入场许可（新能力，替代「顶部当前卡」）

**规则：会话成为 `current` 之前，必须先获得一个席位。**

| 情形 | 行为 |
| --- | --- |
| 目标会话已绑某席 | 正常切换，不动绑定 |
| 有空席 | 切换到该会话的同时**自动绑定**到空席，卡片立即显示 |
| 八席全满 | **不允许静默进入**：弹出「替换哪一席」选择器（列出八席当前任务）；用户选定 → 只替换那一席；用户取消 → 留在原会话 |
| 来源是看板内部（点席/收工/新建） | 不触发许可（本来就有席） |

判定来源：比较 `current` 变化与看板内部动作的时间窗（内部动作置 `pendingSeat`/`creatingSeats` 标记，许可逻辑跳过）。

**为什么不是顶部卡**：顶部卡只是多一个入口，用户仍要「跳」；入场许可保证「看板外不存在当前会话」，从源头消除 M2。

### S4 绑定生命周期（不动）

- 仍是四条解绑路径；新逻辑**不得**引入第五类。
- `reconcile` 的「列表未就绪不动」「seeded 后不补位」两条铁律保持不变。

### S5 数据迁移（v3 → v4）

- 一次性清洗：解绑「已归档且不在当前工作区」的绑定，其余原样保留。
- 写入 `dismissed: SessionId[]`（墓碑）：用户关掉/归档过的会话 id，播种时永久排除，防止 M3 复活。
- 迁移必须幂等：重复执行不改变结果。

## 6. 风险与回滚

| 风险 | 处理 |
| --- | --- |
| `archivedSessionIds` 读不到 | 降级：只按「当前工作区成员 + updatedAt」播种；STAB-01 标 skip 并记录 |
| 迁移误删绑定 | 迁移只解绑「已归档 + 跨工作区」，其余不动；迁移前整份 store 备份到 `dsh-agent-grid.bindings.v3.bak` |
| 许可弹窗被忽略（用户不管它） | 保持原会话，不切换；弹窗可关闭，后续再触发 |
| 用户已经习惯旧播种 | 保留 `seeded` 语义，不强制重排；只有清空/迁移时才按新规则 |

## 7. 待确认（已查一轮）

1. **`archivedSessionIds` 客户端不可直接读** —— 已确认：它只存在于 `dsh-client-ui-workspace` 内部的 `rowState` store（`pin-order` / `tree` / `stores` 都是包内模块，不是服务）；`uiSession` / `dsh-api-session-controller` 都没有 archive 相关 API。
   因此 S1 的归档过滤有两条路：
   - **7a 宿主侧读**：`lib/index.js` 在服务端读 workspace store（`~/.dsh/storages/workspace.json` 同源数据）并作为服务暴露给客户端；改动大、依赖宿主内部形状，需再过一次 contract。
   - **7b 降级**：只用「当前工作区成员 + `updatedAt` 倒序」播种，配合 S5 墓碑 —— 不动宿主内部，风险最低。**建议先走 7b**。
2. 「当前会话」= 宿主 `uiSession.current`（契约层已验证是 binding source）。**关键未验证项**：插件能否在 `current` 变化前拦截？若不能拦截，只能「事后纠正」——切进来后立刻补绑或弹替换框，并在用户取消时切回原会话（STAB-11 的取消路径即为此设计）。
3. 是否需要「手动置顶/锁定某席」—— 本策略不做，留作后续。
